## 1. 제품 개요

KMC Beauty Native는 뷰티샵 운영을 위한 iOS·Android 모바일 앱이다. 예약, 시술 메뉴, 직원, 고객 전화번호부, 매출 현황을 앱 하나에서 관리한다.

| 항목 | 내용 |
|------|------|
| 플랫폼 | iOS · Android (Expo SDK 54 · React Native 0.81.4). Expo 기본 웹 실행 설정(`npm run web`)도 남아 있다 |
| 앱 식별자 | `com.antam2010.kmcbeautynative` (iOS `bundleIdentifier` · Android `package`) |
| 앱 버전 | `1.0.0` (`app.json`) |
| 연동 대상 | KMC Beauty 백엔드 REST API(주소는 환경 변수 `EXPO_PUBLIC_API_BASE_URL`로 주입), 기기 연락처(`expo-contacts`) |
| 개발 형태 | 1인 개발. 계속 개발 중인 제품 |

백엔드 코드는 이 저장소에 없다. 이 문서는 백엔드를 앱이 호출하는 연동 대상으로만 다룬다.

## 2. 대상 사용자

### 2.1 주 사용자

주 사용자는 60대인 샵 오너의 어머니다(SPEC-HOME-001, SPEC-BOOKING-001). 매일 하는 일은 세 가지다.

1. 오늘 예약 확인
2. 예약 등록
3. 고객 찾기

그래서 첫 화면에서 오늘 할 일을 바로 찾게 하고 큰 글씨·높은 대비·넓은 터치 영역을 우선한다(6.2절).

### 2.2 계정과 역할

- 계정의 역할은 서버가 정한다. 앱의 타입 정의는 `ADMIN`·`MASTER`·`MANAGER`·`STAFF`·`USER`다(`src/types/unified.ts`의 `UserRole`).
- 앱은 역할에 따라 화면을 나누지 않는다. 역할은 프로필 화면에 표시만 하고 권한 판정은 서버가 한다. 서버가 403을 돌려주면 앱은 강제로 로그아웃한다.
- 초대 가입과 직원 연결 요청에는 역할을 담지 않는다. 초대 가입자의 역할은 서버가 초대 코드로 결정한다(SPEC-SECURITY-001).

### 2.3 여러 샵 운영

계정 하나가 여러 샵에 속할 수 있다. 로그인한 뒤 샵을 고르면 이후 모든 API 요청의 `X-Shop-ID` 헤더에 그 샵 ID가 실린다. 화면 위쪽의 샵 이름(`ShopHeader`)을 누르면 "다른 상점을 선택하시겠습니까?" 확인 창이 뜨고 "상점 선택"을 고르면 샵 선택 화면으로 가서 샵을 바꿀 수 있다.

## 3. 화면 구성

### 3.1 시작 흐름

진입 화면(`app/index.tsx`)이 저장된 로그인 상태와 샵 선택 상태를 보고 세 곳 중 하나로 보낸다.

| 상태 | 이동할 화면 |
|------|------------|
| 로그인하지 않음 | 로그인 `/login` |
| 로그인했지만 샵을 고르지 않음 | 샵 선택 `/shop-selection` |
| 로그인했고 샵도 고름 | 메인 탭 `/(tabs)` |

### 3.2 메인 탭

| 탭 | 파일 | 주요 내용 |
|----|------|----------|
| 홈 | `app/(tabs)/index.tsx` | 오늘의 예약, 새 예약 버튼, 오늘 요약 |
| 예약 | `app/(tabs)/booking.tsx` | 달력 보기·목록 보기, 예약 등록·상세·수정 |
| 관리 | `app/(tabs)/management.tsx` | 직원 관리, 전화번호 관리, 시술 메뉴 관리 |
| 프로필 | `app/(tabs)/profile.tsx` | 내 정보, 비밀번호 변경, 앱 정보, 로그아웃 |

### 3.3 그 밖의 경로

- `/monthly-dashboard`: 월간 현황 화면. 앱 안에서 이 경로로 이동하는 코드는 없다. 홈은 같은 컴포넌트(`MonthlyDashboard`)를 모달로 띄운다.
- `+not-found`: 없는 경로 안내.

## 4. 핵심 기능

### 4.1 로그인과 초대 가입

- 이메일과 비밀번호로 로그인한다. 요청은 OAuth2 폼 형식이다(`POST /auth/login`).
- 액세스 토큰은 기기 보안 저장소(`expo-secure-store`)에만 둔다. 리프레시 토큰은 서버가 HttpOnly 쿠키로 관리한다. 요청이 401로 실패하면 앱이 `POST /auth/refresh`로 액세스 토큰을 새로 받아 원래 요청을 다시 보낸다.
- "아이디 기억하기"를 켜면 이메일을 기기에 저장한다.
- 초대 코드를 받은 사람은 로그인 화면의 가입 모드에서 초대 코드·이름·이메일·비밀번호·전화번호를 입력해 계정을 만든다(`POST /users`). REFACTORING_GUIDE.md에 따르면 이렇게 만든 계정은 초대한 샵에 자동으로 연결된다.
- 하드코딩된 데모 계정 로그인은 제거했고 `__tests__/loginFormDemo.test.tsx`로 다시 들어오지 않게 지킨다.

### 4.2 샵 선택과 등록

- 샵 목록에서 하나를 고르면 서버에 선택을 기록하고(`POST /shops/selected`) 메인 탭으로 이동한다. 성공하면 햅틱으로 알린다.
- 샵 선택 화면에서 새 샵을 등록할 수 있다(`ShopRegistrationModal`).
- 서버가 `SHOP_NOT_SELECTED` 오류를 돌려주면 어느 화면에 있든 샵 선택 화면으로 이동한다.

### 4.3 오늘 중심의 홈 화면 (SPEC-HOME-001)

- **오늘의 예약**: 오늘 예약을 시간순으로 보여 준다. 항목을 누르면 예약 상세(`UnifiedTreatmentModal`)가 열린다. API를 따로 부르지 않고 이미 받아 둔 이번 주 예약에서 오늘 것만 골라 만든다. 이번 주 예약 조회가 실패하면 오류 안내 대신 빈 목록이 되어 "오늘 예약이 없습니다"로 보인다(로드맵 3번). 일요일에는 이번 주 범위가 다음 주로 계산돼 목록이 늘 비어 있다. 기기 시간대가 한국 표준시이면 오전 9시 전에는 전날 날짜로 예약을 고른다(로드맵 6번).
- **새 예약**: 화면 폭을 채우는 큰 버튼(최소 높이 56)이다. 누르면 예약 탭으로 이동한다.
- **오늘 요약**: 오늘 매출과 오늘 예약 건수, 두 숫자만 보여 준다. "자세히 보기"를 누르면 월간 현황 모달이 열린다.
- 당겨서 새로고침을 지원한다. 오늘 요약을 불러오지 못하면 "다시 시도" 버튼이 있는 오류 화면을 보여 준다(SPEC-UX-001).
- 예전 홈에 있던 주간 달력 위젯과 인기 시술·고객 인사이트·VIP 섹션은 홈에서 뺐다. 프로필의 "준비중" 메뉴 두 개(프로필 수정·알림 설정)도 같은 작업에서 없앴다.

### 4.4 예약 등록·조회·수정 (SPEC-BOOKING-001)

- **달력 보기**: 날짜마다 예약 건수를 표시한다. 날짜를 고르면 그날 예약 목록을 보거나 "이 날짜에 예약하기"로 등록을 시작한다. 화면 위쪽의 "빠른 예약" 버튼(새 예약·오늘 예약·내일 예약)으로도 바로 등록을 시작할 수 있다. 기기 시간대가 한국 표준시이면 날짜 칸이 하루씩 당겨져 날짜가 실제 요일보다 한 칸 뒤에 놓이고 그달 말일은 누를 수 없다(로드맵 6번).
- **목록 보기**: 예약을 20건씩 불러오고 목록 끝에 닿으면 다음 페이지를 이어 받는다. 상태별 필터가 있다.
- **예약 등록**(`BookingForm`, 전체 화면 모달): 고객 검색·신규 고객 등록, 시술 선택(가격·시간 조정), 담당 직원, 예약 시간, 결제 방법(카드 `CARD`·현금 `CASH`·외상 `UNPAID`), 메모를 입력한다.
  - 등록에 성공하면 그때 고른 담당 직원을 기억해 두었다가 다음 등록 때 그 직원이 직원 목록에 있으면 자동으로 고른다.
  - 오늘 날짜로 등록할 때는 현재 시각 이후의 첫 시간대를 눈에 띄게 표시한다. 그 시간을 고르라고 강요하지는 않는다. 다만 예약 탭이 이미 예약된 시간 목록을 폼에 넘기지 않아서 예약이 있는 시간도 빈 시간으로 다룬다(로드맵 6번).
  - 화면에서 고른 담당 직원과 결제 방법이 저장 요청에서 빠지던 버그를 고쳤다. 요청 본문은 `buildTreatmentPayload` 한 곳에서 만들고 테스트로 지킨다. 다만 폼에서 조정한 시술 가격은 지금도 요청에 들어가지 않고 메뉴의 기본 가격이 저장된다(로드맵 6번).
  - 등록에 성공하면 별도 안내창 없이 폼이 바로 닫히고 햅틱으로 알린다. 달력 보기에서는 갱신된 달력이 성공을 보여 준다. 목록 보기는 자동으로 다시 불러오지 않아서 당겨서 새로고침해야 새 예약이 보인다.
- **상세와 수정**: 상세 모달에서 수정 화면(`EditTreatmentModal`)으로 들어가 고객·시술·담당 직원·시간·상태·결제 방법·메모를 바꾼다.
- **예약 상태**: 서버 상태값은 `RESERVED`(예약됨)·`VISITED`(방문함)·`COMPLETED`(완료)·`CANCELLED`(취소됨)·`NO_SHOW`(노쇼) 다섯 가지다. 수정 화면에서 고를 수 있는 값은 예약됨·완료·취소됨·노쇼 네 가지다.
- **예약 취소**: 상태를 "취소됨"으로 바꾸는 방식이다. 서비스에는 `DELETE /treatments/{id}`를 보내는 `remove()`가 있다. REFACTORING_GUIDE.md에는 백엔드가 이 요청을 `CANCELLED` 전환으로 처리한다고 적혀 있다. 다만 지금 이 메서드를 부르는 화면은 없다.

### 4.5 월간 현황

- 월을 앞뒤로 옮기며 매출 현황, 월간 총계, 월간 인기 시술을 본다(`MonthlyDashboard`).
- 홈의 "자세히 보기" 버튼이나 머리글의 달력 아이콘으로 연다. 모달이 닫혀 있는 동안에는 컴포넌트를 마운트하지 않으므로 월간 데이터도 요청하지 않는다(SPEC-PERF-003).

### 4.6 시술 메뉴 관리

- 시술 메뉴를 추가·수정·삭제하고 메뉴마다 세부 항목(이름·소요 시간·기본 가격)을 관리한다(`TreatmentMenuManagement`).
- 예약 등록 화면과 같은 메뉴 데이터를 공유 캐시로 함께 쓴다.

### 4.7 직원 관리와 초대 코드

- 샵의 직원 목록(이름·역할·주 소유자 여부·이메일·상태)을 본다(`StaffManagement`). 상태는 백엔드가 주지 않는 값이라 앱이 항상 "활성"으로 채운다(`useShopUsersQuery`의 `status: 'active'`).
- "직원 초대 코드 생성"으로 초대 코드를 만든다. 유효 기간은 1시간·6시간·12시간·1일·3일·7일·30일 중에서 고르고(기본 30일), 코드를 복사하거나 현재 코드를 지우고 새로 만들 수 있다(`InviteCodeGeneratorModal`).
- 직원 행의 수정 버튼과 상태 전환 버튼은 아직 안내 문구만 띄운다(미구현). 기존 계정 연결·주 소유자 지정·연결 해제 API는 서비스(`UserApiService`)에 있지만 화면에서 부르지 않는다.

### 4.8 전화번호부와 연락처 동기화

- 고객 전화번호부를 검색·추가·수정·삭제한다(`PhonebookManagement`). 항목은 그룹·이름·전화번호·메모로 이루어진다.
- 연락처 동기화(`ContactSyncModal`)는 기기 연락처 접근 권한을 받은 뒤 기기 연락처를 서버 전화번호부로 옮긴다. 마지막 동기화 시각은 기기에 기록한다.
- 예약 등록·수정 화면에서도 고객을 검색하고 전화번호 중복을 확인한 다음 새 고객을 등록할 수 있다.

### 4.9 프로필

- 내 정보(이메일·역할·가입일·현재 샵)를 보여 준다.
- 새 비밀번호를 두 번 입력해 비밀번호를 바꾼다. 현재 비밀번호는 묻지 않는다.
- 앱 정보와 로그아웃 메뉴가 있다.

## 5. 주요 사용 시나리오

1. **아침에 오늘 예약 확인**: 앱을 연다 → 홈의 "오늘의 예약"에서 시간순 목록을 본다 → 항목을 눌러 고객·시술·담당 직원을 확인한다. 지금 코드에서는 오전 9시 전과 일요일에 이 목록이 맞지 않는다(4.3절, 로드맵 6번).
2. **전화로 들어온 예약 등록**: 홈의 "새 예약"을 눌러 예약 탭으로 간다 → 달력에서 날짜를 고르고 "이 날짜에 예약하기"를 누른다(또는 "빠른 예약" 버튼을 누른다) → `BookingForm`에서 고객을 검색한다(없으면 그 자리에서 등록) → 시술을 고른다 → 담당 직원은 최근 선택값이 이미 들어가 있다 → 시간을 고른다(오늘 날짜면 현재 시각 이후의 첫 시간대가 강조돼 있다) → 저장한다. 저장하면 폼이 닫히고 달력과 홈 데이터가 갱신된다.
3. **방문 후 처리**: 예약 탭에서 예약을 열어 수정한다 → 상태를 완료·취소됨·노쇼 중 하나로 바꾸고 결제 방법을 기록한다.
4. **새 직원 합류**: 관리 탭 → 직원 관리에서 초대 코드를 만들어 복사해 전달한다 → 새 직원이 로그인 화면의 초대 가입으로 계정을 만든다 → 로그인 → 샵 선택.
5. **휴대폰 연락처 가져오기**: 관리 탭 → 전화번호 관리 → 동기화 → 연락처 권한을 허용한다 → 기기 연락처가 서버 전화번호부에 등록된다.
6. **월 마감 확인**: 홈 → "자세히 보기" → 월간 현황에서 월을 옮겨 가며 매출과 인기 시술을 확인한다.
7. **샵 바꾸기**: 화면 위 샵 이름을 누른다 → 확인 창에서 "상점 선택"을 고른다 → 샵 선택 화면에서 다른 샵을 고른다. 이후 요청에는 새 샵 ID가 실린다.

## 6. 지켜야 할 제약

아래 세 가지는 기능을 추가하거나 고칠 때 깨면 안 되는 규칙이다. 규칙마다 2026-10-16에 측정한 현재 상태를 함께 적었다. "지켜짐"은 적어 둔 확인 방법으로 확인한 범위에서만 뜻이 있다. 측정 방법과 파일별 목록은 `tech.md` 6~8절에 있다.

### 6.1 보안과 개인정보 (SPEC-SECURITY-001)

| 규칙 | 현재 상태 |
|------|----------|
| 액세스 토큰은 `expo-secure-store`에만 저장하고 AsyncStorage에 평문 토큰을 쓰지 않는다 | 지켜짐. `expo-secure-store`를 import하는 파일은 `authStore.ts` 하나다. `secureHybridStorage`는 AsyncStorage에 쓰기 전에 토큰을 `null`로 비운다(코드 확인) |
| 로그에 토큰·비밀번호를 남기지 않는다. 운영 빌드에서도 `console.error`는 남으므로 오류 로그에 담기는 내용까지 살핀다 | 위험 있음. `base.ts`에 `console.error`가 10곳 있고 `__DEV__` 가드는 없다. 로그인·초대 가입 요청 본문이 이 경로를 지난다(코드 경로 확인, 기기 재현 안 함). 로드맵 1번 |

의존성 취약점(npm audit 84건)은 규칙과 별도로 로드맵 2번에 정리했다.

SPEC-PERF-003 spec.md §3은 9개 항목을 다룬다. 항목 1~6의 대상 파일은 예약 목록·전화번호부·시술 메뉴 관리·달력·홈·월간 현황이다. 로케일 포맷 규칙(항목 7)도 이 파일들에 적용된다. 항목 8(스토어 셀렉터 전환)은 9개 파일, 항목 9는 직원 목록이 대상이다. 아래 현재 상태는 코드 전체 기준이다.

## 9. 로드맵

남은 리팩토링 후속 작업과 이번 문서 갱신 중 확인한 문제를 우선순위별로 정리했다. 아직 SPEC으로 만들지 않은 후보다.

### 9.1 우선순위 높음

1. **운영 빌드 로그의 비밀번호 노출 위험 제거** (SPEC-SECURITY-001)
   - `src/api/services/base.ts`의 `post()`는 요청이 실패하면 요청 본문을 `console.error`로 남긴다(`requestData`). 422 응답이면 본문을 `JSON.stringify`해 한 번 더 남긴다. 이 파일에는 `__DEV__` 가드가 하나도 없다.
   - babel 설정은 운영 빌드에서 `console.error`를 지우지 않는다.
   - 로그인(`POST /auth/login`, 비밀번호가 든 폼 데이터)과 초대 가입(`POST /users`, `password` 필드가 그대로 든 객체)이 이 경로를 지난다.
   - 로그인·가입·비밀번호 변경이 실패하면 AxiosError 객체를 통째로 `console.error`에 넘기는 곳도 있다(`app/login.tsx`, `src/stores/authStore.ts`, `components/forms/LoginForm.tsx`, `components/forms/InviteSignupForm.tsx`, `app/(tabs)/profile.tsx`). AxiosError는 요청 본문을 `config.data`에 담고 있다.
   - 코드 경로는 확인했지만 실제 기기 로그로 재현하지는 않았다.
2. **의존성 취약점 정리** (SPEC-SECURITY-001)
   - 2026-10-16 `npm audit` 결과는 84건(critical 1, high 63, moderate 20)이다. 운영 의존성만 보면(`--omit=dev`) 73건이다.
   - critical은 전이 의존성 `shell-quote` 1건이다. high 이상으로 표시된 직접 의존성은 `axios`, `expo`, `react-native`, `jest`, `jest-expo`, `@anthropic-ai/claude-code`다. 잠금 버전 `axios` 1.18.1은 1.20.0 미만을 대상으로 한 권고 여러 건에 걸린다.
   - 항목마다 앱 번들에 실제로 들어가는지와 실행 경로에 영향이 있는지 확인한 뒤 업그레이드 순서를 정한다(`tech.md` 6.4절).
3. **조용한 실패 제거** (SPEC-UX-001 REQ-UX-007)
   - 서비스 읽기 7개가 요청 실패를 예외로 알리지 않고 빈 값을 돌려준다. `getWeeklyTreatments`·`getMonthlyTreatments`·`getAllWithDetails`·`getAllContacts`·`getContactsByGroup`(`[]`)와 `getCurrentInviteCode`(`null`)는 모든 실패를 삼킨다. `getCurrentShopUsers`는 첫 요청(`getSelected`)의 실패만 삼켜 `[]`를 돌려준다. 직원 목록 요청의 실패는 그대로 던진다(`structure.md` 6.10절, 요청 실패를 흉내 낸 임시 테스트로 확인).
   - 그래서 홈의 `weeklyError` 안내와 예약 폼·시술 메뉴 관리의 메뉴 로드 실패 알림은 나타날 수 없고 실패가 "오늘 예약 없음"·빈 달력·빈 메뉴로 보인다.
   - 서비스가 오류를 던지게 바꾸고 이 동작을 서비스 경계 아래에서 검사하는 테스트를 둔다. 지금 테스트는 서비스를 모킹해서 이 문제를 잡지 못한다.
4. **연락처 동기화의 데이터 무결성 위험**
   - `getAllContacts`가 실패를 삼키면 연락처 동기화는 서버 연락처가 하나도 없다고 판단해 모든 기기 연락처의 등록(`create()`)을 시도하고, 마지막 동기화 시각을 성공으로 기록한다(`src/services/contactSync.ts` 494·520·541행). 대체 조회 경로(560~595행)는 예외가 날 때만 실행돼 이 경우에는 돌지 않는다.
   - 정적 판독 결과다. 실제로 중복 등록이 생기는지는 서버의 중복 처리에 달려 있어 확인하지 못했다. 3번과 함께 다룬다.
5. **품질 기준선 회복**
   - `npx tsc --noEmit` 오류 2건: `components/modals/EditTreatmentModal.tsx` 123행·395행. 이전 SPEC들이 "기준선"으로 남겨 둔 오류다.
   - `npm run lint` 오류 2건: `src/types/unified.ts`가 `ShopUserResponse`를 `./shop`과 `./user` 양쪽에서 다시 내보낸다. 경고 5건(`src/api/client.ts` 1건, `src/stores/authStore.ts` 4건)도 함께 정리한다.
6. **예약 날짜·시간·가격 처리 오류 수정**
   - 주간 예약 조회(`treatmentApiService.getWeeklyTreatments`)는 일요일에 실행되면 다음 주 월요일부터 일요일까지를 요청한다. 요일 값 0(일요일)을 따로 다루지 않기 때문이다. 홈의 오늘의 예약은 이 목록에서 오늘 것만 고르므로 일요일에는 늘 비어 있다.
   - `toISOString()`(UTC 기준)의 날짜 부분을 잘라 날짜 문자열을 만드는 곳이 9개 파일에 21곳 있다. 기기 시간대가 한국 표준시(UTC+9)이면 오전 9시 전에는 "오늘"이 전날이 된다. 그래서 홈은 전날 날짜로 오늘의 예약을 고르고 오늘 요약도 전날 날짜로 조회한다. 예약 탭의 "새 예약"·"오늘 예약"은 전날, "내일 예약"은 오늘 날짜로 폼을 연다. 월간 예약 조회의 종료일은 시각과 관계없이 말일보다 하루 이르다(2026년 10월이면 `2026-10-30`).
   - 같은 원인으로 달력(`src/utils/calendarUtils.ts`의 `generateCalendarDates`)의 날짜 칸이 하루씩 당겨진다. 2026년 10월이면 이달 칸이 9월 30일로 시작해 10월 30일로 끝난다. 날짜가 실제 요일보다 한 칸 뒤에 놓이고 말일은 다음 달 칸으로 그려져 누를 수 없다.
   - 예약 등록 폼에서 조정한 시술 가격(`customPrice`)이 저장 요청에 들어가지 않는다. `buildTreatmentPayload`는 메뉴의 기본 가격(`menuDetail.base_price`)을 보내고 조정한 소요 시간(`customDuration`)만 반영한다. 폼의 합계는 조정한 가격으로 보여 주고 예약 수정(`EditTreatmentModal`)은 조정한 가격을 보낸다. SPEC-BOOKING-001 이전 코드도 같았다.
   - 예약 탭은 예약 폼에 이미 예약된 시간 목록(`reservedTimes`)을 늘 빈 배열로 넘긴다. 이 목록을 채워 넘겨야 할 달력의 `onNewBookingRequest` 콜백이 호출되지 않기 때문이다. 그래서 폼은 예약된 시간을 표시하지 못하고 첫 시간대 강조도 기존 예약을 무시한다.
   - 예약 등록과 수정이 보내는 시각 형식이 다르다. 등록은 시간대 없는 현지 시각(`2026-10-17T14:00:00` 형태)을, 수정은 `toISOString()` 결과(UTC, 끝에 `Z`)를 보낸다. 서버가 두 형식을 같은 시각으로 저장하는지는 확인하지 못했다.
   - 확인 방법: 첫째~넷째 항목은 jest 임시 테스트로 확인했다(2026-10-17). 날짜 항목은 `TZ=Asia/Seoul`에서 요청 파라미터와 달력 칸을 출력했고 일요일 범위는 `TZ=UTC`에서도 같았다. 화면에 미치는 영향과 다섯째·여섯째 항목은 코드를 읽어 판단했으며 기기(Hermes)에서는 확인하지 않았다. 지금 테스트는 이 문제들을 잡지 못한다. 서비스를 모킹하거나 날짜 문자열로 달력 칸을 찾고, 조정 가격과 기본 가격을 같은 값으로 두기 때문이다.

### 9.2 우선순위 중간

7. **CI 품질 워크플로 추가**: 테스트·린트·타입 검사를 돌리는 CI가 없다. PR마다 `npm test`, `npm run lint`, `npx tsc --noEmit`를 실행하게 하고 `typecheck` npm 스크립트도 만든다.
8. **참조되지 않는 코드와 레거시 위치 정리**
   - 정적 import가 0건인 파일: `src/services/storage/userDataService.ts`, `components/modals/StaffRegistrationModal.tsx`, `components/navigation/AuthNavigator.tsx`, `src/types/models.d.ts`, 배럴 파일 `src/api/services/index.ts`·`src/ui/index.ts`.
   - `src/services/contactSync.ts`는 사용 중이지만 레거시 위치에 있고 서비스 안에서 `Alert`·`Linking`을 직접 부른다. 기기 연락처·서버 동기화 로직과 화면 쪽 안내를 나눠 옮긴다.
   - 앱 코드가 직접 import하지 않는 선언 의존성(`dayjs`, `expo-image`, `expo-web-browser`)은 depcheck 같은 도구로 확인한 다음 정리한다.
9. **`BookingForm` 경계 예외 해소**: 폼이 도메인 서비스를 직접 부르고 query 무효화까지 한다(`structure.md` 6절). 컨테이너와 프레젠터로 나누거나 이 방식을 공식 규칙으로 정한다. `EditTreatmentModal`이 직원·메뉴를 공유 query 대신 직접 조회하는 문제와, 캐시 대상인 예약 목록 보기가 아직 react-query로 옮겨지지 않은 문제(`structure.md` 6.9절)도 함께 다룬다.
10. **테스트 커버리지 확대**: `app/`·`components/`·`hooks/`·`contexts/`·`src/` 전체 기준 줄 커버리지는 26.63~26.81%다(2026-10-16에 같은 명령을 세 번 실행한 범위). TRUST 5 목표치 85%와 차이가 크다.
11. **SPEC-UX-001 잔여 미준수 정리** (정적 탐색 기준, `tech.md` 8절)
   - 라벨 없는 아이콘 전용 터치 요소 31곳(6개 파일)
   - 14 미만인 `fontSize` 값 26곳(8개 파일)과 `Typography.fontSize.xs`(12pt) 참조 4곳
   - 아이콘 전용 터치 요소 34곳 모두 `hitSlop`이 없다. 그중 26곳(7개 파일)은 스타일로 추정한 크기가 44 미만(24~40)이다(런타임 측정 아님)
   - 예약 상세 모달(`UnifiedTreatmentModal`)의 상태 배지 대비 1.52~3.66:1(5종 모두 4.5 미만). 예약 목록 배지를 검사하는 `contrast.test.ts`는 색 값을 복사해 쓰므로 컴포넌트 값이 바뀌어도 함께 바뀌지 않는다
12. **직원 관리의 미구현 기능 정리**: 수정·상태 전환 버튼이 안내 문구만 띄운다. 직원 상태는 백엔드에 없는 값이라 항상 "활성"으로 표시된다. 구현하거나 숨긴다. 이 화면 아이콘 버튼의 라벨은 11번에서 함께 다룬다.
